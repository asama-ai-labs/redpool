# AGENTS.md

Rules for coding agents working in the Redpool repository. Humans should read [CONTRIBUTING.md](CONTRIBUTING.md) and [docs/REDPOOL_CONTRIBUTOR_GUIDE.md](docs/REDPOOL_CONTRIBUTOR_GUIDE.md); this file states the same rules in the form an agent needs.

## Python: use `uv`

This repository is a **uv** workspace (root `pyproject.toml`, `uv.lock`; the workspace member is `redfish-snapshot`). Run Python through **uv**, not bare `python` / `python3` / `pip` / `venv`.

| Instead of | Use |
|------------|-----|
| `python script.py` | `uv run python script.py` |
| `pip install …` / `pip install -e .` | `uv sync --all-packages --all-extras` |
| `pytest` / `ruff` in a manual venv | `uv run pytest`, `uv run ruff …` |
| Console scripts from `[project.scripts]` | `uv run redpool-proxy`, `uv run redfish-snapshot`, etc. |

Use `--all-packages`: a plain `uv sync --extra dev` removes the `redfish-snapshot` workspace member and its tests fail to collect.

```bash
# BAD
python scripts/generate_redfish_inventory_exporter_golden.py
pip install -e .

# GOOD
uv run python scripts/generate_redfish_inventory_exporter_golden.py
uv sync --all-packages --all-extras
```

## Where logic lives

Put **vendor- and model-specific** behavior in Redpool normalization: the `normalizers/` tree (prefetch, `field_map`, `version_overrides`, vendor-specific modules). That is where vendor strings get canonicalized, path quirks get fixed, and schema differences across BMCs get smoothed out.

These stay **generic** (transport, scraping, metrics shape, forwarding). Don't add one-off vendor/model branches here to compensate for payload quirks; fix them in `normalizers/` instead.

- **`redpool/`**: proxy request/response plumbing, orchestration, config. No vendor-specific hacks that belong in a normalizer.
- **`third_party/redfish-inventory-exporter/`**: collector. Generic collection and mapping to the exporter metric schema.

This follows the project principle of fixing inconsistencies in Redpool normalization when the data already exists in raw Redfish payloads (see `docs/REDPOOL_CONTRIBUTOR_GUIDE.md`).

**Third-party trees need confirmation first.** `third_party/fishymetrics/` (`github.com/Comcast/fishymetrics`) is upstream code.

- Do not modify it in drive-by changes.
- Before planning edits there, confirm with the user that they want it changed, rather than fixing behavior in `normalizers/` or a first-party component.

Quick check:
- New `if vendor == "X"` or model-specific parsing in a collector or proxy file? Move it to `normalizers/` (or extend an existing vendor normalizer).
- Tempted to patch `third_party/fishymetrics/` for a BMC quirk? Stop and ask. Prefer normalization or a first-party wrapper.

## Fixtures and golden files

The capture corpus (`fixtures/`) is the `redpool-fixtures` submodule: captures of lab servers only, dedicated under CC0 1.0, and a `NOTICE.md` on provenance and use. If the submodule is not checked out, tests that need it skip through the `requires_fixtures` marker, and the golden and normalized-output scripts have nothing to read. `REDPOOL_FIXTURES` points those scripts at another corpus checkout.

- A change to the corpus is a pull request to `redpool-fixtures` plus a pointer bump here. Without fixtures, prove a normalizer change with a unit test that builds a minimal synthetic payload inline (see the existing `tests/test_*.py`). Don't invent fixture files, and don't copy real serials, MAC addresses, host names or IP addresses into tests; use placeholders such as `SN-TEST-0001`, `00:1B:44:AA:BB:CC` and `192.0.2.10`.
- Models outside the public corpus are regenerated by maintainers who hold those captures.

### Prometheus golden files: no hand edits

Do **not** hand-edit golden Prometheus exposition files under `fixtures/`:

- `redfish_inventory_exporter_direct.prom` / `redfish_inventory_exporter_redpool.prom`
- `fishymetrics_direct.prom` / `fishymetrics_redpool.prom`

Always regenerate them with the repo scripts:

- `uv run python scripts/generate_redfish_inventory_exporter_golden.py` (add `--no-proxy` for direct)
- `uv run python scripts/generate_fishymetrics_golden.py` (add `--no-proxy` for direct)

Use `--model Vendor/Model` to limit scope while iterating.

If generated output is wrong, or direct vs. redpool diverges in an undesirable way, change Redpool normalization in `normalizers/` (or the first-party proxy/config as appropriate), then regenerate. Never patch `.prom` files in the editor to "fix" metrics.

### Triaging redfish-inventory-exporter output

If `redfish-inventory-exporter` metrics or golden output look incorrect, empty, or inconsistent with what the BMC should report (including `Unknown` labels, zeros, or missing rollups), treat it **first** as a **Redpool normalization** problem. The upstream Redfish payload may omit fields, use vendor shapes, or need canonicalization before gofish and the collector see it.

- Prefer fixing behavior in `normalizers/` (prefetch, `field_map`, vendor modules, `version_overrides`) so the JSON served through the proxy matches what standard Redfish clients expect.
- Do **not** assume `third_party/redfish-inventory-exporter/` is wrong, and don't patch it for BMC-specific quirks before checking whether `normalizers/` can supply or reshape the missing data from the raw payload.

## Normalizers (`normalizers/`)

### Mental model

- **Two phases:** `prefetch(ctx)` may call the Redfish client and write only to `ctx.prefetched`. `field_map()` and `version_overrides()` must be **pure** relative to `ctx.data` + `ctx.prefetched` (literals, nested dicts, `lambda ctx: …`).
- **Registry:** `register_base(path_pattern, …)` first, then `register_resource(path_pattern, vendor, …)` for overrides. Collections use `register_collection(path_pattern, mapping)`. Submodules register at import time. Importing `normalizers` must keep loading `systems`, `chassis`, `managers`, and `firmware_inventory` so entries exist before the proxy serves traffic.
- **Resolution:** Path patterns are slash-separated collection segments (e.g. `Systems/Processors`, `Chassis/Drives`). They must match the strings used in `get_normalizer_for_path` in `redpool/proxy.py`. Typos silently skip normalization.

### Adding or extending a resource

1. Prefer a **base class + vendor subclasses** when behavior differs by BMC vendor. Use **one module** with helpers when the fix is vendor-agnostic.
2. Register in the package `__init__.py` next to related imports, in a consistent order: base → vendors → collection → subpackages.
3. If the BMC uses non-standard URLs, colocate request and URL behavior with the vendor normalizer. Use `register_request_rewrite` from `normalizers/request_rewrites.py`. Put segment maps only in `normalizers/url_rewrites.py`, and only when they are global segment aliases (see the existing `PCIDevices` → `PCIeDevices` pattern).
4. After behavior changes, add a unit test. Regenerate the Prometheus goldens of the models in `fixtures/` with the repo scripts (maintainers regenerate the rest) (see "Prometheus golden files" above). Don't hand-edit `.prom` files.

### Schema target

- One `@odata.type` per resource, written as a string literal in `field_map`. Older versions of that resource migrate to it (see "Fixed `@odata.type`" below). The field map is that version's property set, and every standard name must exist in that DMTF schema.
- If an older BMC omits a field-map property, copy it from another standard field, a linked resource, or OEM when the value is present. Otherwise emit `""`, `{}`, or `[]`. Use `null` only when the schema type rejects an empty string, such as an enum. Never fabricate a value.
- Inventory, topology, or telemetry with no standard property goes in `Oem.Redpool`.
- Dell, HPE, and Lenovo `MemoryLocation` tables follow the vendor memory-channel manual.

### Fixed `@odata.type`

Redpool stamps one `@odata.type` per resource. Older payload versions migrate to that version. The version is not chosen from the payload, from which properties are filled, or from the BMC's version string.

Write the version as a string literal in that resource's `field_map`. Don't store it in a constant, and don't add a function that returns it.

```python
# BAD
PORT_ODATA_TYPE = "#Port.v1_20_0.Port"

def port_odata_type(ctx):
    if is_dmtf_port(ctx):
        return PORT_ODATA_TYPE
    return ctx.data.get("@odata.type")

# GOOD: NetworkPort's version is the field map literal
"@odata.type": "#NetworkPort.v1_4_3.NetworkPort",
```

`#Port` and `#NetworkPort` are different resources. A Port document is `#Port.v1_20_0.Port`. A NetworkPort document is `#NetworkPort.v1_4_3.NetworkPort`. Neither stays on the version the BMC sent.

### Vendor normalizers follow the captures

The base field map is the schema shape the captures share. A property that no model sends is not in that map, and it is not defaulted to `[]`.

When one vendor sends a value under the wrong name or place, map it in that vendor's module for the resource (`register_resource`). Don't branch in the shared base on whether the payload happens to contain the key.

```python
# BAD: processor_metrics/base.py
"CStateResidency": lambda ctx: ctx.data.get("CStateResidency", []),
"CoreVoltages": lambda ctx: (
    {"Reading": ctx.data["CoreVoltages"]} if ctx.data.get("CoreVoltages") else OMIT
)

# GOOD
# No capture has CStateResidency or CoreVoltages, so base.py does not mention them.
# A vendor that sends them maps CStateResidency onto CoreMetrics and
# CoreVoltages to CoreVoltage in normalizers/.../processor_metrics/<vendor>.py.
```

### Field maps and evaluation

- Keep `field_map()` mostly declarative. Extract non-trivial transforms to **named functions** in the same file, or in `normalizers/_shared/` if reused across resources.
- No presence check in the base map (`if` the OEM name is set, rename it, else omit). Optional properties no capture contains are left out of the base map. A vendor that does send them is handled in that vendor's resource module.
- `evaluate()` recurses into **dict** values and invokes **callables**. Other values, including **lists**, are left as-is. Structure maps accordingly.
- `version_overrides()` keys are **exact** `@odata.type` strings, which are fragile across firmware. Prefer base `field_map` logic when possible. Use overrides only for schema versions that truly need a different shape.

### Prefetch

- Use prefetch for **linked resources** or enrichment that can't be expressed from the current JSON alone. Avoid duplicate GETs already implied by the response.
- If prefetch builds the **entire** normalized document (rare), override `ResourceNormalizer.normalized_body_from_prefetch(ctx)` to return that dict. `redpool/proxy.py` then skips `field_map` and `version_overrides`. The default is `None`. Don't add `isinstance` checks for concrete normalizers in the proxy.

#### Prefetch-only full body (sparse output): LogEntry pattern

**Problem:** A `field_map` keyed by a fixed superset of property names, with lambdas like `ctx.prefetched["__x__"].get(k)`, re-materializes every key when evaluated. Missing properties become explicit JSON `null` values, a dense object, even when prefetch already built a sparse, Redfish-shaped document.

**Reference implementation:** `BaseLogEntryNormalizer` stores the sparse v1.16.1 body in `ctx.prefetched["__log_entry__"]` via `build_log_entry_v161` in `normalizers/_shared/log_entry/v161.py`. It overrides `normalized_body_from_prefetch` to return that dict, so consumers get sparse LogEntry JSON rather than a null-filled projection. `LOG_ENTRY_FIELD_MAP_KEYS` remains for callers that evaluate `field_map` without the hook (tests, tooling).

**When to use the hook:** Any resource where the correct shape is "omit absent keys", or where it can't be expressed as a pure field map without polluting the output. Implement it on the normalizer class and keep `redpool/proxy.py` generic.

### Shared and cross-cutting code

- Reuse `normalizers/_shared/` for logic shared across chassis, systems, and managers (e.g. log entry shapes, memory ECC helpers). Keep vendor forks in `normalizers/_shared/<area>/<vendor>.py` or next to the resource they serve.
- **Manufacturer / PCI vendor strings:** use `normalizers/vendor_id.py` (and related helpers) for canonical names instead of duplicating substring rules.
- **Server vendor** strings passed into `register_resource` must match how metadata normalizes vendor names for lookup (`entry.vendors.get(vendor, base)`).

### Maintainability checklist

- **Deterministic:** same input JSON + same prefetch results → same output. No time, random, or network calls in field maps.
- **Narrow changes:** make the smallest field-level or path-level fix that resolves consumer drift. Don't fabricate values the payload doesn't contain. Empty placeholders and copies from data the payload already has are required so every model emits the target shape.
- **Naming:** match Redfish property names in output unless the project already canonicalizes a different spelling for stability.
- **Discoverability:** one obvious place per resource (`normalizers/<area>/<resource>/`). Avoid orphan modules that no package `__init__.py` imports.

### Anti-patterns

- Vendor or model `if` chains in `redpool/` or collectors for payload quirks. That belongs in normalizers.
- Large lambdas with multi-screen logic. Use named functions plus tests.
- New URL or request behavior only in the proxy. Prefer registration APIs in `normalizers/url_rewrites.py` / `normalizers/request_rewrites.py` tied to the normalizer.

## Normalization rules stay in the vendor normalizer

`redpool/proxy.py` fetches, rewrites URLs, and calls the registered normalizer. It contains no resource or vendor normalization.

Put the behavior in the vendor override for that resource under `normalizers/` (`register_resource`, that class's `field_map` / `prefetch` / `version_overrides`, or the request-rewrite hook registered beside it).

### Don't add to the proxy

- Vendor or model branches (`if vendor == "HPE"`, model string checks)
- Property fixes, enum mapping, OEM relocation, or schema cleanup
- Special cases in path classification so a rewritten URL still normalizes

A client path that isn't on the BMC (HPE `Systems/PCIeDevices/{id}` served from `Chassis/PCIeDevices/{id}`) is handled by the rewrite hook in that resource's vendor module. Example: `normalizers/systems/pci_devices/hpe.py` merges the chassis device and normalizes it with `HpeSystemsPCIeDeviceNormalizer` inside `_hpe_after_200_merge`.

```python
# BAD: proxy.py
except Exception:
    if collection_parts:  # treat a missing HPE PCIeDevice URL as a resource
        current_path_type = ResourceType.RESOURCE

# GOOD: normalizers/systems/pci_devices/hpe.py
return normalize_resource(HpeSystemsPCIeDeviceNormalizer(), ctx)
```

### Don't branch on one vendor in base.py

A normalization that applies to a single vendor belongs in that vendor's `field_map`, `prefetch`, or `version_overrides`. Don't implement it as `if x: do y else do z` in the shared `base.py`.

When the same behavior applies to more than one vendor, it stays in `base.py`.

```python
# BAD: chassis/network_ports/base.py
def link_status(ctx):
    if ctx.vendor == "Lenovo":
        return "LinkUp" if ctx.data.get("LinkStatus") == "Up" else "LinkDown"
    return ctx.data.get("LinkStatus")

# GOOD: chassis/network_ports/lenovo.py
m["LinkStatus"] = lenovo_port_link_status

# GOOD: base.py when more than one vendor shares it
"LinkStatus": omit_if_null(
    lambda ctx: canonicalize_network_port_link_status(ctx.data.get("LinkStatus"))
)
```
